## Решения для экспертной проверки

- Роли PostgreSQL разделяют владельца миграций, web-приложение и отчётное чтение. Они **не** являются гостем/игроком/модератором BA. Игроки входят через Identity, а авторство и права модератора проверяет API (NFR03).
- `capacity` — дополнительные игроки. `active_participants` в отчёте — активные отклики, не доказательство физического присутствия (US09–11, W05). Бронирование площадки не создаётся (W01).
- Статус отчётного представления соблюдает Cancelled → Expired → Full → Open. Часы БД используются для истечения; представление не хранит устаревающий статус (NFR04).
- Триггер защищает уже записанное решение от случайного UPDATE/DELETE/TRUNCATE, поддерживая аудит US06/14. Он не является бессрочной политикой хранения: US19 и §2.8 требуют отдельно согласованного административного удаления/обезличивания, включая снимки. Владелец БД технически может изменить триггер в таком контролируемом процессе.
- Отчётная роль видит только три представления. Email замаскирован полностью; хеши, stamps, токены, подробности жалоб и JSON-снимки не выдаются. Представления не публикуются HTTP-endpoint и не являются экспортом пользовательских данных US19.
- Демонстрационные аккаунты используют `example.invalid`, псевдонимы `[ДЕМО]`; игры заполняются только в явно разрешённой локальной `_demo` или изолированной тестовой базе. Они не считаются органическим использованием, KPI или подтверждёнными посещениями (§2.9).
- Не собираются дата рождения, история перемещений и признаки здоровья; координаты относятся к общественной площадке (§2.8, W04). Маскирование для эксперта не заменяет GDPR-процессы, оценку законных оснований или проверку правил участия несовершеннолетних.

## Что ещё нельзя считать выполненным

Нагрузочный NFR01; UX-пилот минимум с пятью участниками и целевой сценарий NFR02; TLS в реальном окружении (часть NFR03); семидневная доступность NFR05; ночные backup и проверка восстановления NFR06; обработка фото NFR10 не подтверждены. Для NFR03 проверены авторизация API и ограниченная роль PostgreSQL, но серверного deployment сейчас нет. Автоматизированные браузерные проверки не являются человеческим usability-тестированием, а проверки отдельных элементов доступности не означают полной сертификации WCAG.

## KPI из BA

Названия и цели ниже сохранены по Table 2.1 BA; отдельного KPI органического использования в BA нет.

| KPI | Точное название в BA | Цель BA | Текущее состояние |
| --- | --- | --- | --- |
| KPI1 / G1 | `Find suitable court and open game, then join` | Не менее 80% пилотных пользователей (минимум пять) выполняют задачу без помощи за 3 минуты; сравниваются baseline и prototype. | Не проверено: согласованный человеческий пилот и baseline отсутствуют. |
| KPI2 / G2 | `Publish immediate recruitment from a place card` | Не менее 80% пользователей (минимум пять) публикуют корректный запрос за 60 секунд от открытия формы до подтверждения. | Не проверено: автоматизированные сценарии не заменяют измерение с участниками. |
| KPI3 / G3 | `Freshness and provenance` | 100% проверенных карточек показывают время обновления; истёкшие сессии исключаются из доступных для вступления не позднее 60 секунд после истечения. | Частично проверено автоматическими тестами времени/истечения; полный KPI-протокол по карточкам не проведён. |
| KPI4 / G1–G3 | `Core scenario correctness` | Все acceptance criteria Must проходят в зафиксированных release checks; последнее онлайн-место не назначается дважды. | Частично проверено: конкурентное последнее место покрыто тестом, но KPI не достигнут, пока отсутствуют Must US07, US12 и US19 и не пройдены все их критерии. |

## Рекомендуемый порядок дальнейшей реализации

1. После решения владельца о публичных персональных данных подготовить безопасные публичные копии документов; историю изменять только отдельным согласованным действием.
2. Реализовать US07 вместе с безопасной обработкой изображений и NFR10.
3. Добавить отдельную модель текущего присутствия US12, не смешивая её с `participations`.
4. Спроектировать и реализовать экспорт/удаление US19 вместе с политикой хранения и обезличиванием связей.
5. Последовательно добавить Should-истории US15–17; US18 начинать после определения источников, ограничений AI и приватности.
6. Реализовать объяснимые рекомендации US20 на основании явных предпочтений, не по скрытым чувствительным признакам.
7. Провести нагрузочные, человеческие UX, backup/restore и длительные эксплуатационные проверки, затем подготовить TLS deployment и измерение KPI.

Критерии эксперта по Git, словарю, нормализации, ролям и SQL-объектам — дополнительные материалы сдачи, а не новые пользовательские функции BA. Исходники опубликованы в `https://github.com/WHYJDM/SteamIRL`; server deployment отсутствует.
