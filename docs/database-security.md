# Доступ к PostgreSQL и секреты

С 11 ноября 2026 года web-приложение запускается только под ограниченным пользователем. Суперпользователь нужен для первоначального создания ролей и передачи владения выделенной базой; его строка подключения не передаётся в сервис `api`.

## Матрица доступа

По умолчанию префикс ролей `steamirl`. Для другой базы в том же кластере задаётся другой `DatabaseRoles__Prefix` / `DATABASE_ROLE_PREFIX`, чтобы не менять пароли работающего приложения.

| Роль | Назначение | Разрешено | Запрещено |
| --- | --- | --- | --- |
| Администратор установки | Первоначальный bootstrap выделенной БД | Создать роли, передать владение | Не используется HTTP-приложением |
| steamirl_migrator | Владелец схемы и миграций; отдельные административные CLI-команды | DDL в своей БД, миграции, заполнение, назначение Moderator через CLI, выдача GRANT | SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS; роли не наследует |
| steamirl_app | Все запросы HTTP-приложения | SELECT разрешённых таблиц; INSERT/UPDATE операционных записей; INSERT решений; DELETE только кеша идемпотентности | DDL, создание/наследование ролей, изменение AspNetRoles/AspNetUserRoles, UPDATE/DELETE аудита, DELETE истории, чтение reporting и журнала миграций |
| steamirl_reader | Контролируемое чтение экспертом | USAGE reporting, SELECT трёх представлений | Чтение базовых таблиц public, паролей/токенов/жалоб/аудитных снимков; любые мутации |

Владелец миграций не является пользователем приложения. Прямые запросы runtime-роли не обходят запрет самоназначения роли Moderator. Права пользователя на чужие строки внутри разрешённых runtime-таблиц дополнительно ограничивает API; здесь не заявляется реализация row-level security.

Точный allowlist — [DatabaseAccess.cs](../src/SteamIRL.Api/Data/DatabaseAccess.cs). Автоматических GRANT на все будущие таблицы нет: после новой миграции требуется явное решение о правах и повтор `--grant-database-access`. Для транзакционных блокировок `SELECT … FOR UPDATE/SHARE` runtime имеет UPDATE соответствующих операционных таблиц.

## Первичная настройка

`--bootstrap-database` выполняется только администратором **выделенной** базы SteamIRL. Он создаёт три непривилегированные роли, устанавливает пароли из окружения, отбирает права PUBLIC на базу/схему и передаёт владение существующих таблиц/представлений мигратору. Последовательности Identity переходят вместе с таблицей. Роли с неожиданными привилегиями/членством отклоняются, а не используются молча.

Далее мигратор выполняет `--migrate`, затем `--grant-database-access`; только после этого запускается web с логином приложения. Это отдельные одноразовые сервисы `bootstrap → migrate → grant-access` в Compose. Bootstrap повторяемый, но смена переданных паролей меняет соответствующие роли: не генерировать новый `.env` поверх действующего.

Не изменять первоначальный `POSTGRES_USER` при использовании уже созданного Docker-тома: сохранить логин администратора, которым том инициализирован. Смена значения `.env` сама по себе не создаёт пользователя в старом томе. Для локальной существующей БД скрипт инициализации поддерживает отдельный `STEAMIRL_ADMIN_CONNECTION`. Рабочие данные не удаляются и том не пересоздаётся.

При нормальном старте `DatabaseAccess.VerifyApplication` проверяет права фактического `current_user`: привилегированные атрибуты, владение БД/объектами, CREATE в public и членство в других ролях. Небезопасный запуск отклоняется. `Testing:SkipDatabaseRoleCheck` устанавливается только внутри интеграционной фабрики: старые тесты мигрируют одноразовые базы и имитируют недоступную БД. В `.env`, Compose, обычных настройках и скрипте запуска этот флаг отсутствует; Start-LocalApi удаляет его из окружения. Отдельные тесты запускают полный HTTP-сценарий под реально ограниченным логином и проверяют сам guard.

## Представления и аудит

- `reporting.account_directory`: ID, публичный псевдоним и полная маска `***@***`. Исходный email, PasswordHash, нормализованные адреса, stamps и токены отсутствуют. Идентификатор/псевдоним остаются данными аккаунта: это ограниченный экспертный доступ, не обещание полной анонимизации.
- `reporting.location_catalogue`: только Approved-площадки и включённые виды спорта.
- `reporting.session_overview`: дополнительные места, активные отклики и вычисленный статус; скрытые площадки/выключенные активности не раскрываются. Отклики не выдаются за подтверждённое присутствие.
- `protect_moderation_decision()` и триггеры запрещают UPDATE/DELETE/TRUNCATE решений, даже при случайном запросе владельца таблицы. Функция не имеет SECURITY DEFINER; произвольные SQL-команды не выполняет, search_path фиксирован. Владелец может изменить схему для отдельно согласованной политики хранения/US19; runtime не может отключить защиту.

## Работа с секретами

`scripts/New-LocalSecrets.ps1` генерирует четыре разных случайных значения, не печатает их и не перезаписывает существующий файл. `.env.example` содержит только пустые поля; действующие `.env`, ключи Data Protection, локальные данные PostgreSQL и результаты QA исключены из Git. Ограничить доступ к файлу средствами ОС; для публичного размещения использовать защищённое хранилище секретов и TLS.

В CI пароли генерируются заново для каждого запуска и маскируются в логах; фиксированных рабочих паролей в YAML нет. Тестовый пароль Identity также создаётся в памяти. `scripts/Check-Repository.ps1` проверяет отслеживаемые пути и поддерживаемые сигнатуры ключей/токенов/литеральных строк подключения, не выводя найденные значения. Это дополнительная проверка, а не доказательство обнаружения любых секретов. В локальном Git нет `.env`, `.local`, приватных ключей или дампа данных.

Миграции и `database/schema.sql` содержат DDL и публичные справочные записи, а не выгрузку пользовательских аккаунтов. Проверка словаря читает системные каталоги, не строки пользователей. `pg_dumpall` и выгрузки кластерных паролей не используются.

Технические основания: [привилегии PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-priv.html), [CREATE VIEW и модель доступа](https://www.postgresql.org/docs/17/sql-createview.html), [default privileges](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html). Права владельца нельзя свести к обычному GRANT, поэтому владелец и runtime разделены.
