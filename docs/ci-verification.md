# Проверка CI и изоляции интеграционных тестов

Дата: 12 ноября 2026 года.

## Удалённый запуск

Последний доступный GitHub Actions run для коммита `2fa8e17` — [43246831509](https://github.com/WHYJDM/SteamIRL/actions/runs/43246831509). Backend собрался, но тесты завершились с результатом 84 passed / 27 failed. Frontend прошёл, а `containers` был пропущен из-за зависимости от упавшего backend. Поэтому этот запуск не является зелёным CI и не подтверждает контейнерный запуск.

Все падения имели PostgreSQL-код `42P07`: параллельные экземпляры `ApiFactory` применяли первую EF-миграцию к одной и той же `steamirl_test` и одновременно пытались создать Identity-таблицы, начиная с `AspNetRoles`. `AccountTests`, `CatalogueTests`, `LocationTests` и `SessionTests` используют отдельные `IClassFixture<ApiFactory>`, а xUnit вправе выполнять классы параллельно. Ранее каждый factory получал одну строку `STEAMIRL_TEST_DATABASE`; проверка префикса защищала рабочую БД, но не обеспечивала изоляцию классов.

## Локальное исправление

Общий `ApiFactory` теперь:

- принимает только административное подключение, у которого имя базы начинается с `steamirl_test`;
- создаёт для каждого экземпляра случайную базу `steamirl_test_api_*`;
- направляет приложение и прямые подключения теста только в эту базу;
- применяет миграции дважды, сохраняя проверку повторяемости;
- после остановки host удаляет только принадлежащую factory тестовую базу;
- при ошибке инициализации также пытается убрать только эту созданную базу.

Специализированные fixtures модерации и проверки ролей сохраняют свои отдельные тестовые базы. `steamirl` и `steamirl_demo` в подготовке или очистке тестов не участвуют. Параллельный запуск и все assertions сохранены; тесты не отключались и не ослаблялись.

Два последовательных локальных прогона Release на PostgreSQL 17 после исправления: в каждом **111 passed, 0 failed, 0 skipped**. После второго прогона запрос к `pg_database` показал **0** баз с префиксом `steamirl_test_api_`: cleanup временных баз завершился. Это локальный результат; новый удалённый run появится только после отдельного разрешённого commit/push.

## Ограничение проверки

`docker compose config --quiet` с временными значениями обязательных переменных завершился успешно. Полный запуск выполнить не удалось: Docker CLI установлен, но локальный Docker Desktop Linux Engine недоступен. Поэтому сборка образов, `up --wait` и HTTP-проверки через nginx **не объявляются успешными**; их должен выполнить будущий удалённый `containers` job после прохождения backend и frontend.
