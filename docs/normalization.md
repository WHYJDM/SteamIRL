# Нормализация, ключи и ограничения

Основание — BA_Nikitsenkau_Aliaksei 2.docx, разделы 2.5–2.8 и Appendix A. Нормализация предметной реляционной модели рассматривается отдельно от технических кешей, форматов Identity и исторических документов аудита. Полные физические поля и DDL: [словарь](data-dictionary.md), [схема связей](logical-schema.md), [миграции](../src/SteamIRL.Api/Data/Migrations), [DDL](../database/schema.sql).

## 1НФ

В операционных таблицах поля хранят одно значение заданного типа. Список поддерживаемых видов спорта вынесен в `location_activities`, список предложенных видов спорта — в `submission_activities`; повторяющиеся колонки Sport1/Sport2 не используются. Отклики игроков — отдельные строки `participations`. Роли и утверждения Identity представлены таблицами связей.

## 2НФ

У связей составные ключи: `(LocationId,ActivityId)`, `(SubmissionId,ActivityId)`, `(SessionId,UserId)`, `(UserId,RoleId)`. Условия участия (`JoinedAt`, `LeftAt`) зависят от всей пары «игра + пользователь»; `IsEnabled` — от всей пары «площадка + активность». Название спорта не копируется в строку участия или связи.

## 3НФ предметных фактов

| Отношение | Функциональная зависимость | Что вынесено отдельно |
| --- | --- | --- |
| activities | id → slug, name, description; slug — альтернативный уникальный идентификатор | Название спорта хранится в справочнике |
| locations | Id → текущие название, адрес, координаты, доступ, состояние и версия | Пользователи и виды спорта не описываются в строке площадки |
| public_profiles | UserId → DisplayName | Email и хеш находятся в приватном Identity-аккаунте |
| sessions | Id → пара площадка/активность, OrganiserId, вид, время, вместимость, уровень, инвентарь, отмена | Названия площадки/спорта/организатора получаются JOIN; числа участников и статус вычисляются |
| participations | (SessionId,UserId) → JoinedAt, LeftAt | Вместимость и сведения аккаунта не дублируются |
| location_activities | (LocationId,ActivityId) → IsEnabled | Названия площадки и спорта не дублируются |
| location_submissions | Id → автор, целевая площадка, предложенная версия, состояние, время | LocationId не определяет предложенные поля: у места несколько разных версий предложений |
| submission_activities | ключ (SubmissionId,ActivityId), иных предметных атрибутов нет | Нет строковых списков активностей |
| content_reports | Id → AuthorId, одна цель, причина, подробности, состояние, время | Название цели и псевдоним автора получаются JOIN |
| moderation_decisions | Id → одно обращение, ModeratorId, действие, причина, время | Псевдоним модератора не копируется; по обращению одно окончательное решение |

Непервичные предметные атрибуты не используются для хранения названий/характеристик других сущностей. Составной FK `sessions(LocationId,ActivityId)` указывает на допустимую пару, а не только на независимо существующие место и спорт.

## Технические исключения физической схемы

- ASP.NET Core Identity хранит нормализованные имена/email, security/concurrency stamps и служебные поля. Это формат выбранного фреймворка и индексов; пользовательская часть не утверждает строгую 3НФ для всех его производных полей.
- `Fingerprint` — производный технический отпечаток для конкурентной проверки дублей. Он не заменяет справочник и не является источником названия, адреса или координат.
- `OriginalDataJson`, `BeforeJson`, `AfterJson` — неизменяемые исторические документы. Их значения намеренно не следуют будущим изменениям площадки: это доказательство того, какие сведения проверял модератор (US06/14), а не повторная текущая запись площадки.
- `ResponseJson` — кеш исходного ответа для идемпотентности с ограниченным сроком. Он не используется для расчёта текущих свободных мест. Текущая карточка запрашивается отдельно.

Таким образом, нормализованное ядро отделено от специально сохранённых снимков и технических производных. Это обоснование конкретных решений, а не заявление, что произвольное содержимое JSON нормализовано до 3НФ.

## Ограничения и индексы

PK запрещают повтор строки; FK с RESTRICT сохраняют историю и исключают сирот. CHECK проверяют координаты, версии, перечисления, 1–30 дополнительных мест, `EndsAt>StartsAt`, время выхода и ровно одну цель жалобы/решения. Частичные уникальные индексы запрещают одинаковые открытые жалобы, повтор Pending-предложения автора и второе точное одобрение нового места. Участие уникально по паре; результат команды — по пользователю и ключу.

Индексы по активности/окончанию игры и площадке/окончанию обслуживают поиск; по организатору/созданию — лимит немедленных приглашений; по состоянию/времени — очереди модерации; по автору/времени — собственные обращения; по пользователю/выходу — историю участия. Полный перечень, включая уникальные и FK-индексы, генерируется в словарь. При малом демонстрационном наборе PostgreSQL может выбрать последовательное чтение: наличие индекса само по себе не доказывает выигрыш. Нагрузочный NFR01 ещё не подтверждён.
