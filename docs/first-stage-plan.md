# SteamIRL: план первого этапа

Статус: реализованы основа, аккаунты и профили, каталог и площадки, создание и поиск игр, участие, вместимость, отмена и личная история. Следующим шагом добавлены предложения площадок, исправления, жалобы на площадки/игры и модерация — US05–06, US13–14 в пределах существующих типов материалов. Проверки и ограничения описаны в [отчёте об играх](sessions-verification.md) и [отчёте о модерации](moderation-verification.md). Полный MVP и итоговые KPI/NFR ещё требуют следующих этапов.

## Результат этапа

Пользователь открывает каталог, выбирает волейбол, находит проверенную площадку Вильнюса на карте или в списке, открывает игру и присоединяется. Другой пользователь может создать запланированную игру или запросить игроков прямо сейчас, изменить число мест и отменить свою игру.

Это работающий промежуточный результат. Для полного MVP остаются отзывы, безопасные фото, сообщения о присутствии и управление персональными данными. Жалобы и снятие отзывов/фото будут подключены вместе с этими типами материалов.

## 1. Основа проекта

Предлагаемая структура:

```text
SteamIRL.sln
src/
  SteamIRL.Api/
  SteamIRL.Web/
tests/
  SteamIRL.Api.IntegrationTests/
  SteamIRL.Web.E2E/
docs/
compose.yaml
.github/workflows/
```

Backend — модульный монолит ASP.NET Core Web API с EF Core и PostgreSQL. Внутри группируем код по функциям: Accounts, Activities, Locations, Sessions. Отдельные сервисы и дополнительные проекты создаются при реальной необходимости.

Frontend — React с TypeScript. Карта подключается через отдельный компонент; API возвращает данные независимо от поставщика карт. Внешние зависимости подключаются после выбора условий использования. Локальная разработка сначала может идти через список, но этап считается завершённым только с рабочей картой и её резервным представлением.

Результат: оба приложения и база запускаются через Docker Compose; первая миграция и начальные данные воспроизводимы; настройки-примеры не содержат секретов. CI собирает backend/frontend и запускает доступные автоматические проверки. Деплой и его окружение добавляются позже, после выбора хостинга.

## 2. Аккаунты и публичный профиль

Истории: **US01, US02**.

- Использовать ASP.NET Core Identity для учётных данных и ролей.
- Для SPA того же сайта предлагается серверная cookie-аутентификация с HttpOnly cookie и защитой изменяющих запросов от CSRF. Разработку и продакшен организовать через общий origin; настройки HTTPS, срока сессии и cookie зафиксировать в конфигурации.
- Реализовать регистрацию, вход, выход и получение своего аккаунта. Публичный профиль возвращает только разрешённые поля.
- Обрабатывать ошибки входа без раскрытия существования аккаунта, запретить изменение чужого профиля.

Проверка: регистрация не создаёт второй аккаунт с тем же нормализованным email; неавторизованные изменения запрещены; публичные ответы не содержат приватных данных; чужой профиль изменить нельзя.

## 3. Каталог и площадки

История: **US03**, основа для **US04**.

- Создать каталог и модель локаций по [ER-диаграмме](data-model.md).
- Подготовить небольшой проверенный набор площадок Вильнюса. Для каждой хранить источник и дату проверки в файле начальных данных; не выдавать вымышленные записи за реальные места.
- Добавить отдельный тестовый набор, включая локацию с двумя активностями, чтобы проверить общую идентичность места.
- Сделать выбор активности, список, карту и карточку площадки с временем обновления. Предусмотреть загрузку, ошибку, отсутствие результатов и резервный список при недоступной карте.

Проверка: смена активности не создаёт вторую локацию; неодобренные места не выдаются; при отказе карты карточки и игры доступны через список.

## 4. Создание и поиск игр

Истории: **US04, US08, US09**.

- Добавить запланированную игру: площадка, активность, начало, окончание, уровень, инвентарь и 1–30 дополнительных игроков.
- Добавить «Нужны игроки сейчас»: площадка и активность уже выбраны, количество меняется кнопками, срок действия по умолчанию — час. Свободного текста в быстрой форме нет.
- Время начала немедленной игры устанавливает сервер. Проверки срока действия, дублей и частоты выполняются транзакционно.
- Дать фильтры по активности, временному интервалу и уровню. Для первого этапа фильтр времени означает пересечение интервала игры с выбранным интервалом поиска. Отменённые и истёкшие игры исключаются; полные можно показать с явным статусом и без возможности вступления.
- При повторном немедленном приглашении показать существующую игру и переход к её редактированию.

Проверка: неверные интервалы, неподдерживаемая активность, лишние приглашения и повторные сетевые отправки не создают некорректные записи. Заполненная игра тоже запрещает создание дублирующего немедленного приглашения.

## 5. Участие и управление игрой

Истории: **US10, US11**.

- Добавить вступление, выход и раздел «Мои игры» для участника и организатора.
- Организатор меняет вместимость и отменяет игру; действия над чужой игрой запрещены.
- Выполнить протокол блокировок и идемпотентности из модели данных.
- Вычислять статус на сервере. Обновлять открытые карточки в пределах 60 секунд, проверять состояние заново при каждом действии.
- Показывать понятные результаты: «Последнее место уже занято», «Игра завершена», «Организатор отменил игру».

Проверка: при 20 одновременных запросах на последнее место проходит ровно один. Повтор вступления или выхода не меняет число мест повторно; вместимость нельзя уменьшить ниже числа участников; выход или увеличение вместимости снова открывают действующую полную игру. Отмена и истечение запрещают новые вступления немедленно на сервере.

## 6. Предварительный контракт API

Пути предлагаются для обсуждения при реализации. Формат ошибок должен содержать стабильный код причины, сообщение и ошибки полей; неожиданные ошибки не раскрывают внутренние детали.

| Метод и путь | Назначение | Истории |
| --- | --- | --- |
| `POST /api/auth/register` | Регистрация | US01 |
| `POST /api/auth/login`, `POST /api/auth/logout` | Вход и выход | US01 |
| `GET /api/me`, `PATCH /api/me/profile` | Собственные данные и изменение псевдонима | US02 |
| `GET /api/profiles/{userId}` | Публичный профиль | US02 |
| `GET /api/activities` | Каталог | US03 |
| `GET /api/locations?activityId=…` | Одобренные локации выбранной активности | US03 |
| `GET /api/locations/{id}` | Карточка площадки | US03 |
| `GET /api/sessions?activityId=…&locationId=…&from=…&to=…&level=…&joinableOnly=…` | Поиск и фильтры; параметры необязательны | US04 |
| `GET /api/sessions/{id}` | Актуальная карточка и статус игры | US04, US11 |
| `POST /api/sessions` | Создать Planned или Immediate | US08–09 |
| `PATCH /api/sessions/{id}/capacity` | Изменить количество дополнительных мест | US11 |
| `POST /api/sessions/{id}/cancel` | Отменить собственную игру | US11 |
| `POST /api/sessions/{id}/join`, `POST /api/sessions/{id}/leave` | Вступить и выйти | US10 |
| `GET /api/me/sessions` | Организованные игры и история участия | US10–11 |

Коллекции должны иметь ограничение размера ответа и пагинацию. Для карты требуется загрузка локаций в пределах видимой области с теми же правилами фильтрации и публикации, что и у списка. Даты API однозначно задают момент времени; интерфейс показывает местное время площадки.

## 7. Условия завершения этапа

1. Проект запускается по инструкции из чистого окружения с Docker; миграции и тестовые данные воспроизводимы.
2. Два тестовых аккаунта проходят сценарий «организатор создал → игрок нашёл и вступил → вышел → организатор отменил» в интерфейсе.
3. Проверены US01–04 и US08–11 в пределах описанной реализации. Сохраняется таблица соответствия критериям Appendix A, без заявления о готовности остальных Must-историй.
4. Интеграционные тесты выполняются на PostgreSQL: проверяются последнее место, дубли команд, гонка отмены со вступлением, изменение вместимости и истечение при ожидании блокировки.
5. Несколько браузерных сценариев проверяют вход, поиск и вступление; ошибки и пустые состояния доступны в интерфейсе.
6. Ключевые экраны проверены на ширине 360, 768 и 1440 px, с клавиатурой, видимым фокусом и понятными подписями полей. Для опубликованных текстов и статусов проверяется контраст.
7. В CI проходят сборки и проверки. В документации перечислены выполненные критерии, известные ограничения и способ запуска.

Нагрузочное испытание по NFR01, недельное измерение доступности, восстановление резервной копии и пилот с минимум пятью участниками остаются обязательствами следующих этапов. Завершение этого этапа не означает прохождения всех KPI или готовности к публичному запуску.
